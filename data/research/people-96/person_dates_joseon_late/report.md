# person_dates_joseon_late — 조선 후기 인물 17명 연대 연결

배정된 기존 Person ID 17개에 표시 가능한 연대가 하나도 없었다. 각 ID의 신원을 먼저 확인한 뒤, 한국민족문화대백과사전(한국학중앙연구원) 해당 인물 항목을 새로 내려받아 생몰·재위·활동 연도를 수집했다. 결과는 `result.json`, ID별 처리 상태는 `coverage.json`에 있다.

## 결과 요약

- 배정 17명 중 17명에 연대 클레임을 붙였다(미해결 0명).
- 클레임 39개, 출처 16개(모두 서로 다른 민백 항목 URL), 내려받은 원본 파일 17개.
- `scenes`는 빈 배열이다. 장소·거주 클레임은 만들지 않았고, 재위나 생몰에서 위치를 추론하지 않았다.

## 신원 확인 방법

배정 파일에 함께 온 기존 클레임(관계·인용문)과 labelHanja를 먼저 읽고, 그 지표가 사전 항목에 그대로 나오는지 확인한 뒤에만 연대를 붙였다. 각 ID의 근거는 `coverage.json`의 `identityBasis`와 클레임 `note`에 남겼다. 특히:

- `ent-wpa-sibaek` · `ent-wpa-sibang`: 실록 총서에 성 없이 「時白」 「時昉」로만 적힌 인물이다. 민백 「이시백」·「이시방」 항목이 두 사람 모두 연평부원군 이귀의 아들이며 서로 형제라고 적어, 총서의 부자·형제 관계와 일치하는 경우에만 연결했다.
- `ent-wua-yeongjo` · `ent-wva-jeongjo` · `ent-wwa-sunjo`: 총서에 이름 없이 「大王」으로 적히거나 휘·자만 적힌 ID다. 민백이 적은 성명(이산 李祘), 본명(이공 李玜), 자(형운·공보), 연잉군 봉작 같은 고유 지표가 총서 표기와 맞을 때만 연결했다.
- `ent-wva-jeongjo`와 `ent-wwa-jeongjong`은 사람으로는 같은 정조이지만, 각각 정조실록 총서(大王諱祘)와 순조실록 총서(正宗大王)에서 온 별개의 ID다. 병합하지 않고 같은 사전 항목을 근거로 각각 연대를 붙였으며, 正宗이 곧 정조라는 근거(1899년 묘호 개정 서술)를 `ent-wwa-jeongjong` 쪽 인용문으로 따로 남겼다.
- `ent-wpa-wonjong`(元宗)과 `ent-wva-jinjong`(眞宗), `ent-wva-jangheon-seja`(莊獻世子)는 추존된 이름이다. 붙인 연도는 각각 정원군·효장세자·사도세자로 살아 있던 기간이며, 추존 시점을 생존이나 재위로 바꾸지 않았다. 원종 항목의 고려 원종과의 혼동도 배제했다(민백 「원종」 항목이 "인조의 아버지"로 명기).

## 남긴 공백과 판단

- `ent-wva-sin-hoe`(申晦): 민백 「신회」 항목이 사망 연도를 "미상"으로 적는다. 몰년은 만들지 않고 출생 1706년과 1772년 좌의정·영의정 사실만 붙였다. 활동 연도는 임명 사실 한 해이며 재임 전 구간이 아니다.
- `ent-wva-gim-sangcheol`(金尙喆): 생몰은 확보했으나, 1776년 정조 즉위 시점에 영의정이었다는 문장은 이 사전 항목에 없다. 관직 재임 구간 클레임은 만들지 않았다.
- `ent-wua-sukjong`: 민백 「숙종」 항목에는 총서의 시호 표기 元孝가 실려 있지 않다. 신원은 묘호 肅宗과 영조의 아버지라는 관계로 잡았고, 이 한계를 note에 남겼다.
- 배정 인물과 연결된 기존 사건(`ev-wpa-geouibyeong`, `ev-wva-sungjeongmun-jeukwi`)에는 카탈로그상 연대 클레임이 없어, 기존 사건을 근거로 삼을 수 없었다. 기사 날짜 메타데이터는 원 지시대로 본문 날짜로 환산하거나 인용하지 않았다.

## 수집 절차와 검증

- `https://encykorea.aks.ac.kr/robots.txt`를 먼저 받아 `/Article/Search` 등이 금지된 것을 확인하고, 검색 경로는 쓰지 않았다. 항목 URL은 외부 검색으로 찾고 `/Article/E...` 본문만 직접 내려받았다.
- 모든 요청은 타임아웃 15초, 재시도 최대 1회(`fetch.py`). 내려받은 원본 바이트는 `raw/`에 그대로 있고, URL·수집 시각·HTTP 상태·바이트 길이·sha256을 `manifest.json`에 적었다. 광범위한 아카이브 수집은 하지 않았다.
- 인용문은 내려받은 파일에서 직접 잘라냈다. 이 사전 페이지는 李를 호환 한자(U+F9E1)로 쓰는 곳이 있어 손으로 옮겨 적지 않고 페이지의 문자열을 그대로 슬라이스했다(`build_result.py`).
- `validate_result.py`가 (1) 디스크 바이트의 sha256과 manifest 일치, (2) 인용문이 페이지의 정확한 부분 문자열인지, (3) 클레임의 모든 연도·구간 경계가 인용문 안에 글자 그대로 있는지, (4) URL별 인용문 총합이 25낱말 이하인지, (5) 배정 ID 17개가 모두 entities와 coverage에 있는지를 검사한다. 마지막 실행에서 문제 0건이었다.

## 파일

- `result.json` — sources / entities / claims / scenes(빈 배열) / missing
- `coverage.json` — 배정 ID별 `{id, status, claimIds, identityBasis, reason}`
- `progress.json`, `manifest.json`, `raw/` — 진행 상태와 원본 바이트 및 해시
- `fetch.py`, `extract.py`, `srcdata.py`, `build_result.py`, `validate_result.py` — 수집·조립·검증 스크립트
