## 2. 수집 방법

- 모든 요청은 파이썬 `urllib`, 타임아웃 15초, 재시도 최대 1회(`fetch_lib.fetch`).
- 받은 바이트는 곧바로 `raw/` 에 쓰고 `manifest.json` 에 한 건씩 덧붙이며, 매번 `flush()` + `os.fsync()` 를 부른다. 중간에 끊겨도 그때까지 기록이 남는다.
- robots.txt 는 호스트마다 요청 전에 확인한다. 파이썬 기본 `robotparser` 는 파일 순서대로 첫 일치 규칙을 쓰지만, RFC 9309 와 대형 사이트의 관례는 "가장 긴 일치 규칙이 이긴다"이므로 그 방식으로 다시 구현해 판정했다(`fetch_lib.robots_ok_rfc`). 위키데이터가 `Disallow: /wiki/Special:EntityData/` 아래에 `Allow: /wiki/Special:EntityData/*.` 를 따로 두어 기계 판독용 내보내기를 열어 둔 것을 그대로 따른 결과다.
- robots 가 막은 곳은 요청하지 않았다: `query.wikidata.org`(SPARQL), `download.geonames.org`, `nominatim.openstreetmap.org`, `overpass-api.de`, `hgis.history.go.kr`, 위키미디어의 `/w/`·`/api/` 경로.
- 응답을 받은 요청만 `manifest.json` 에 남는다(404 도 상태 코드 그대로 기록). 연결이 안 되거나 robots 가 막아 보내지 않은 요청은 매니페스트에 없고 `missing` 과 아래 8절에 적었다.
- 좌표를 기억에서 적어 넣은 곳은 없다. `coordinates.json` 의 모든 숫자는 `raw/` 의 파일이나 이 폴더에 원래 있던 `existing-place-anchors.json`·`existing-sites.json` 에서 읽은 값이다. 항목 번호(QID)를 고를 때는 한국어 위키백과 문서가 가리키는 번호로 확인했고, 받은 항목의 표제가 찾던 이름과 다르면 쓰지 않았다.

## 5. 현대 행정구역과 역사 지점의 구분

같은 이름이라도 다음은 각각 다른 줄이며, 좌표를 서로 대신 쓰지 않는다.

- 서울특별시(`rc-seoul-city`) / 조선 한성부(`rc-hanseongbu`) / 경복궁(`rc-gyeongbokgung`)
- 개성시(`rc-kaesong-city`) / 고려 정궁 터 만월대(`rc-manwoldae`) / 1910~1945 개성군 앵커(`rc-kaesong-1910-1945`)
- 경주시 / 월성, 부여군 / 부소산성, 공주시 / 공산성, 진주시 / 진주성, 평양시 / 1910~1945 평양 앵커
- 철원은 세 줄이다. 대한민국 철원군(`rc-cheorwon-county-rok`), 조선민주주의인민공화국 철원군(`rc-cheorwon-county-dprk`), 1910~1945 철원군 앵커(`rc-cheorwon-1910-1945`). 이름만 같을 뿐 같은 행정 실체가 아니라 합치지 않았다. 옹진군도 인천의 같은 이름 군과 구분해 황해남도 쪽만 넣었다.

옛 이름 별칭은 항목 자체가 그 옛 실체일 때만 넣었다(예: `rc-hanseongbu` 의 한성·한양). 현대 도시 기록에는 옛 이름을 붙이지 않았다. 원자료가 별칭으로 싣더라도 이번에 동일 실체를 확인하지 못한 대응(흠남/흥남, 진남포/남포, 나진/라선, 위례성/서울)은 연결하지 않고 `missing` 에 남겼다.

## 7. 좌표 처리 규칙

- 모든 좌표는 WGS84 십진도 경도·위도다. 원자료가 이미 같은 체계라 투영 좌표 변환은 하지 않았다. 변환한 값이 없으므로 변환식도 없다.
- 위키데이터 항목에 순위가 매겨진 좌표 진술이 있으면 우선(preferred) 진술을 쓰고, 없으면 첫 진술을 썼다. 진술이 둘 이상이던 10개 기록은 `coordinateNote` 에 다른 값을 모두 적었다. 표기 자릿수가 정확도를 뜻하지 않으므로 자릿수가 많은 값을 자동으로 고르지는 않았다.
- 원자료가 밝힌 좌표 자릿수가 거친 경우(약 0.017도)는 그 사실을 `coordinateNote` 에 적었다.
- `regionBounds` 는 제주도 한 곳에만 있다. 같은 위키데이터 항목의 최북단·최남단·최동단·최서단 좌표(P1332~P1335)가 실제로 있어 만든 값이고 부속 도서는 포함하지 않는다. 다른 곳은 출처가 경계 상자를 주지 않아 비웠다. 임의로 만든 상자는 없다.
- `entityIds` 는 `existing-catalog.json` 에 실제로 있는 ID 만 넣었고 빌드할 때 검사한다. `anchorPlaceIds` 는 `existing-place-anchors.json` 에 있는 앵커 ID 만 넣었다.
- 순수 기계 좌표 자료에는 인용문을 붙이지 않았다. 인용문은 이용 조건을 밝히는 두 페이지와 재사용한 기존 파일의 근거 문구에만 달았고, 웹페이지당 25낱말을 넘지 않는다.

## 8. 하지 못한 것과 한계

`coordinates.json` 의 `missing` 에 11건으로 적었다. 요약하면:

1. 백두산은 원자료에 순위 없는 좌표 진술이 두 개(약 150km 차이) 있어 어느 쪽인지 가리지 못해 등록하지 않았다.
2. 국가유산청 OpenAPI 가 응답하지 않아 월성·부소산성·공산성·진주성 등의 기관 공식 좌표를 새로 받지 못했다(위키데이터 좌표로 대신했다).
3. 국사편찬위원회 역사지리정보 사이트는 robots.txt 가 전면 금지(`Disallow: /`)라 1910~1945 자료의 정식 자료명·배포 조건을 원 기관 페이지로 확인하지 못했다. 제공자 표기는 기존 저장본과 카탈로그에 적힌 문구(국편 / 국편GIS사업팀)에 근거하며, 재사용 출처의 `license` 필드에도 "확인하지 못했다"고 적었다.
4. 한국민족문화대백과사전에서 시·군 항목의 동경·북위 범위를 얻지 못해 경계 상자를 늘리지 못했다.
5. GeoNames 덤프·Nominatim·WDQS 가 robots 로 막혀 교차 검증용 두 번째 좌표 출처를 확보하지 못했다. 지금 좌표 대부분은 위키데이터 한 곳에 의존한다.
6. 태봉 도성(철원 풍천원), 백제 한성처럼 비정이 갈리거나 접근 가능한 좌표 출처가 없는 곳은 넣지 않았다.
7. 속초는 1910~1945 자료가 군 단위여서 대응 앵커가 없다(당시 양양군). 양양 앵커를 속초 앵커로 쓰지 않았다.
8. 위키데이터·위키백과는 계속 편집되는 자료다. `manifest.json` 의 `fetchedUtc` 와 `sha256` 은 받은 시점의 상태를 가리킬 뿐, 지금 다시 받으면 값이 달라질 수 있다.

이 작업은 지리 좌표만 다뤘다. 인물·사건 서술은 새로 만들지 않았다.

## 9. 재현

```
python harvest_wd.py       # 한국어 위키백과로 항목 식별 -> 위키데이터 좌표 수집 (raw/, manifest.json)
python build_registry.py   # raw/ + 기존 앵커·유적 파일 -> coordinates.json
python make_report.py      # coordinates.json + manifest.json -> report.md
```

`build_registry.py` 는 실행할 때마다 `entityIds`·`anchorPlaceIds` 존재 여부, 장소 ID 중복, 좌표가 한반도 범위(경도 124~132, 위도 33~43.5) 안에 드는지를 검사하고 어긋나면 멈춘다.
