# 많은 파일의 변경 확인 속도 (#83)

읍·면 경계가 추가된 운영 데이터는 변경 확인 대상이 21,762개다. 짧은 API도 먼저 이 목록의
mtime·크기를 확인하는데, Path 객체를 정렬하면서 경로를 반복 비교하는 비용이 커졌다.
[실제 프로파일](signature-83-profile-before.json)에서 정렬이 가장 많은 시간을 차지했다.

정렬 키를 경로 문자열로 한 번 만들고, 파일 존재 확인과 stat을 한 번의 stat으로 합쳤다.
매 요청의 변경 확인은 유지한다. 검사 주기를 늦추거나 응답 내용을 줄이지 않았다.

[c2의 같은 파일 집합 비교](signature-83-comparison.json):

| 검사 | 이전 | 수정 후 |
|---|---|---|
| 변경 확인 4회 | 0.441 / 0.435 / 0.455 / 0.435초 | 0.184 / 0.187 / 0.200 / 0.188초 |
| 파일 수·mtime·크기 | 21,762개 | 모두 일치 |

문자열 정렬로 내부 목록의 순서는 달라지지만 새 순서는 반복 실행에서 같다.
목록은 변경 여부 확인에만 쓰고 원문·검색 결과의 순서로 쓰지 않는다.
실제 파일을 추가·수정·삭제했을 때 감지하는 검사와 서버 API 검사 18개가 통과했다.
이 측정은 독립 프로세스의 파일 확인 시간이며 전체 HTTP 응답 시간은 운영 재검사에서 따로 확인한다.
