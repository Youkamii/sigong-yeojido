# 대용량 검증·TTL 빌드 메모리 (#41)

2026-09-06. 검증기가 모든 원문의 본문·공백 제거 문자열·locator를 메모리에 보관하던 방식을 바꿨다.
이제 전체 파일에서 JSON 구문·필수 필드·ID 중복은 검사하되, ID마다 파일과 바이트 위치만 저장한다.
Claim이 참조한 조각의 원문과 메타데이터를 읽을 때 기존 검증용 값을 만든다.
사료별 조각 수는 색인을 만들면서 집계한다. TTL에 원문을 넣지 않는 규칙은 유지한다.

## 실행 확인

| 데이터 | 결과 | 최대 RSS | 시간 |
|---|---|---:|---:|
| 기존 c2 438,371 chunks | 기존 TTL과 바이트 동일, 17,048 triples | 128,004 KiB | 12.28초 |
| 신규 포함 2,566,920 chunks | 955 Source, 86 claims, 17,136 triples | 571,784 KiB | 94.81초 |

두 실행 모두 digest 86/86 일치, 실패 0이다. 수치는 해당 c2 실행에서 관측한 값이며 부하에 따라 달라진다.
기존 TTL SHA256은 `0987da4c92071a2efd27cec24be7c6e4493f87d65abaf91e70a86dad789daa4b`로 같았다.
신규 전체 데이터 TTL은 802,750 bytes, SHA256 `c0b88e5099cb991415f1c187f519e90b59941df3c123778ac9974071bd381b53`이다.
신규 빌드 로그는 c2 `/tmp/sigong-lazy-new-build.log`에 있다.

원문 인용·digest 변조·없는 chunk·엔티티·깨진 claims를 거부하는 8개 fixture와 전체 흐름 검사를 통과했다.
추가 테스트는 사용하지 않은 본문을 정규화하지 않는지, 같은 chunk를 필요할 때 읽은 값이 기존 방식과
같은지, 참조되지 않은 줄의 JSON 오류·필수 필드 누락·중복 ID도 실패하는지를 확인한다.

`place-gungnae` 엔티티 껍데기가 없어 위치 후보를 건너뛰는 기존 빌더 경고는 남아 있다.
이 변경으로 Claim이나 좌표 후보를 새로 만들지는 않았다. 감시 명령은 새 빌더를 쓰도록 배포 때 다시 시작한다.
